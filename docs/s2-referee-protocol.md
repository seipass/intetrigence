## 0.0 原則

1. **決定論**: `(seed, 席, 両者の着手列)` から全ラウンドが完全再現できること。verify-replay の前提。
2. **対称性**: 席による有利不利は、シートの入れ替えで相殺できる形にする(§2.3)。
3. **ルールは s2-spec.md のみ**: 本書にルール値(攻撃表・cap・遅延など)を書かない。参照で済ませる。
4. **監査可能性**: 思考時間・第 1 候補採用率・採点一致を毎ゲーム記録する(PLAN §3.3)。
5. **飢死させない**: ボットの応答を待つ。時間制限は課さない(PLAN §3.3)。

## 1. マッチ構成

| 項目 | 値 | 出典 |
|---|---|---|
| ラウンド | **3 段階 × 50 ゲーム**(25 seeds × シート 2) | PLAN §1、§1.4 |
| 合格条件 | 段階 1(CC2)・段階 2(clys)= **`wins_topout == 50`**(未決着 0・no contest 0・負け 0)、段階 3(attax)= **`wins_topout >= 48` かつ `turncap == 0`** | goal、§1.4、§7.1.3 |
| ペース | 5 PPS = **12 frame / turn** | PLAN §3.1、s2-spec §11-U9 |
| ターン上限 | **1000 turn** | PLAN §3.1 |
| preview | **5** + hold | s2-spec §2.6 |
| 思考時間 | intetrigence `--ms 100`(8 threads)。**決定論モードは §2.4 の条件を満たす場合のみ** | PLAN §1、§2.4 |
| seed | **25 個**。ラウンド前にコミットで事前確定(§1.5) | PLAN §1 |

### 1.1 seed の扱い

- 1 seed = 1 ゲーム(シートごとに 1 回)。**同じ seed を 2 回プレイする**(シート A / B)。
- seed は `1 ≤ s ≤ 2_147_483_646` の整数。
- seed から RNG への導出は **s2-spec.md §11-U7** のとおり。レフェリーは `derive_seeds(s)` を 1 回だけ呼び、`piece_seed` と `garbage_seeds[slot]` を得る。
- **ラウンド開始時に毎回、導出から初期化し直す**。ラウンド間で RNG を引き継がない。

### 1.2 席(sheet)と slot

| 概念 | 意味 | シートで入れ替わるか |
|---|---|---|
| **席(seat)** | 1 turn 内の解決順序。seat 1 → seat 2 | **入れ替わる** |
| **slot** | ゴミ穴 RNG の割り当て。`slot 0 = intetrigence`、`slot 1 = attax` | **入れ替わらない** |

| シート | seat 1 | seat 2 |
|---|---|---|
| **A** | intetrigence | attax |
| **B** | attax | intetrigence |

- **ピース列は両シートで同一**(`piece_seed` は 1 本。各プレイヤーが自分の袋をその seed から作り、hold で分岐する。§2.2)。
- **ゴミ穴列は bot ごとに固定**(slot が identity なので、シートを変えても同じ bot は同じ穴列)。
- したがって 2 シートの違いは **1 turn 内の解決順序だけ**になる(§3.2)。これが席バイアスを相殺する。

### 1.3 プロファイル

マッチには**プロファイル**があり、replay header に必ず記録する。

| profile | 開始盤面 | 用途 | 最終主張に使えるか |
|---|---|---|---|
| **`official`** | **空盤面** | 最終マッチ、M2 ゲート、M0 | **使える(これのみ)** |
| `defense-stress` など | 決定論的な非空盤面 | M3 の診断(高く積んだ状態からの downstack を短いゲームで多数測る) | **使えない(診断専用)** |

- **最終主張(ラウンドの勝率)は `official` のみで集計する。** 診断プロファイルの勝率と混ぜてはいけない。
- 診断プロファイルを使う場合、**開始盤面を replay header に記録**し、verify は同じ開始盤面から再実行する(行マスク + 穴列、または盤面ハッシュ)。
- 診断プロファイルでも**レフェリーのルールは変えない**(違うのは初期状態だけ)。思考時間・PPS・preview 数・hold は本命と同じ。
- レポートには profile 名を明記し、`official` 以外の数字は「診断」と分けて出す。
- **`official` の開始盤面が空であることは検証可能**であること(header に `start_board: null` を記録し、verify が空盤面から始める)。

> 診断プロファイルは「防御の改善を測る」ための道具であって、勝率の主張を大きくするためのものではない。**profile を明記しない数字は主張に使えない**、という規律で運用する。

### 1.4 ラウンド形式(段階ゲート)

**1 ラウンド = 同一ビルド・同一コミットの intetrigence で、次の 3 段階をこの順に実行する。**

| 段階 | 相手 | ゲーム数 | 合格条件 |
|---|---|---|---|
| **1** | **Cold Clear 2**(最新公開版をコミット固定、TBP 接続) | 25 seeds × 両シート = **50** | **`wins_topout == 50`** かつ `losses_topout == 0` かつ `turncap == 0` かつ `no_contest == 0` |
| **2** | **clys**(citrus610、最新公開版をコミット固定、専用アダプタ) | 25 seeds × 両シート = **50** | **`wins_topout == 50`** かつ `losses_topout == 0` かつ `turncap == 0` かつ `no_contest == 0` |
| **3** | **attax**(`7b38f51` 固定) | 25 seeds × 両シート = **50** | **`wins_topout >= 48`** かつ `turncap == 0`(負け・no contest は 2 まで) |

> **段階順は 2026-11-16 に変更された**(goal `721820d42d69bc91`)。**CC2 → clys → attax** の順で、**前の段階の完全試合が次の段階の前提**。
>
> - **段階 1・2 は完全試合**。50 ゲームすべてが `TopOut` 勝ちでなければならない。未決着(`turncap`)も no contest(`no_contest`)も **1 件たりとも許さない**。
> - **段階 3 だけは 48/50**(勝率 95%)。`turncap == 0` を要求するが、**no contest は 2 件まで許す**(`wins_topout + losses_topout + no_contest == 50` を満たす範囲)。no contest は勝ちでも負けでもないので、48 勝 2 no-contest は 96% で通過する。
> - **5 項目の合計検算は全段階で必須**: `wins_topout + losses_topout + turncap + no_contest + stuck == 50`。合わないレポートは無効。
>
> **なぜ attax が最後か**: attax は S2 非対応(20 行視野・board desync)で **no contest が構造的に出る**唯一の相手。先に S2 非対応だが安定した CC2 / clys で「TopOut で 50 連勝できる」ことを示し、**最後に一番壊れている相手**を測る。

> **2026-11-14 改訂(重要)**: 旧定義は「勝数 = 50 勝 0 敗」だったが、**forfeit を勝ちに数えていた**ため、相手のアダプタ故障率を測っていた。**勝ちに数えるのは `TopOut` だけ**に変更した(§7.1.3)。`forfeit-vision` は「相手の視野制限による不戦」であり、実力の証明ではない。`TurnCap`(未決着)も勝ちに数えない(v1.26)。

- **段階 N が合格しなければ、段階 N+1 以降は実行しない。** 合格条件が「前の段階の合格が前提」だから。
- **attax には 40 行視野の互換パッチを当てる**(§7.3.1、2026-11-14 決定)。**upstream `7b38f51` は 20 行視野**(`ROWS = 20`)なので、高スタックで必ず置けなくなり `forfeit-vision` が頻発する。`forfeit-vision` は勝ちに数えないため、**パッチなしでは段階 3 の 48/50 も原理的に届かない**。
  - パッチは**相手を強くする方向**(視野 20 → 40 行)であり、§7.3 の許容範囲。CC2 / clys の spawn パッチと同じ扱い。
  - 代替案(合格条件を「不戦を除いた決定ゲームの勝率」に読み替える)は、**分母が結果で変わる**ため §7.1.1 の原則と衝突するので**却下**。
- **判定は `TopOut` の勝数で行う**(§7.1.3)。未決着(`turncap`)・不成立(`forfeit`)は勝ちに数えない。
  - 段階 1(CC2)・段階 2(clys): `wins_topout == 50` かつ `losses_topout == 0` かつ `turncap == 0` かつ `no_contest == 0`
  - 段階 3(attax): `wins_topout >= 48` かつ `turncap == 0`
  - 全段階: `wins_topout + losses_topout + turncap + no_contest + stuck == 50`
  - **`wins_turncap` という集計項目は存在しない**(v1.26 以降、`TurnCap` は `winner = None`)。旧式 `wins_topout + wins_turncap >= 45` は `wins_turncap ≡ 0` なので `wins_topout >= 45` と同値だが、**45 は goal ではない**(`docs/s2-rule-audit.md` F4)。
  - **未決着が 1 件でも出たら段階 1・2 は不通過**(未決着は勝ちではない)。**`turncap` は独立した集計項目**として数える(`draws` と混ぜない)。
- **`forfeit-vision` は勝ちに数えない**。相手の視野制限による不戦であり、実力の証明ではない。**別途報告する**(ゲート外)。
- **`forfeit-other` が 1 件でも出たらラウンド不成立**(§7.1.2 のアダプタ故障)。ゲームを無効とし、原因を直して新しい seeds でやり直す。
- **3 段階すべて同じ seeds**(§1.5 で事前確定した 25 個)を使う。相手ごとに seeds を変えない。
- **3 段階すべて同じ条件**: 5 PPS、`--ms 100`、5 preview + hold、`official` プロファイル、1000 turn cap、両シート。
- **再挑戦はラウンド全体のやり直し**。どの段階で未達でも、修正後の**新しいビルド**と**新しい事前確定 seeds**で段階 1 からやり直す。**部分再実行・過去の合格結果とのつなぎ合わせは不可**。
- **段階が 1 つでも未達なら、そのラウンドは失敗**。以降の段階は実行しない(既定)。
  - 失敗した段階より後の段階を**診断目的で実行してもよい**が、その結果は**ラウンドの結果ではない**。レポートでは「診断(ラウンド外)」と明示し、勝率をラウンドの数字と混ぜない。
  - 失敗したラウンドのレポートも**必ず残す**(どこで止まったか、`stop_reason` は何か)。次のラウンドの入力になる。
- 診断プロファイル(`defense-stress` / `garbage-pressure`)の数字は、ラウンドの主張に混ぜない(§1.3)。
- 段階 1・2(CC2 / clys)は **attax への過学習を防ぐ汎化検証**である。両ボットは S2 非対応なので、勝率の解釈をレポートに明記する(§7.2 / §8.5)。
- **CC2 / clys は TBP で 40 行の盤面を受け取る(フル視野)**。したがって **`forfeit-vision` は起きず、決着は `TopOut` か `TurnCap` になる見込み**。これは「本物の TopOut 勝負」であり、汎化検証として望ましい形。
- **`forfeit-other` が 1 件でも出たら、その段階は不成立**(§7.1.3-4)。サードパーティのボットでも例外にしない。原因(相手のコミット・アダプタ・我々のレフェリー)を特定してから、**新しい seeds でラウンド全体をやり直す**。フル視野の相手では `NoMoves` がほぼ起きない(§7 の証明)ので、期待頻度は 0 に近い。
  - 「無効ゲームを除いて 50 ゲームに満たす」ような**事後の補充は禁止**。サンプル数が結果に依存するため。

#### 中断と再開

ラウンドは 150 ゲーム(数時間)なので、中断が起こりうる。

- **中断した場合でも、完了したゲームの replay は保持する**(捨てない)。
- **再開は「同一ビルド + 同一 seeds」のときだけ許す**。`(seed, sheet)` 単位で完了済みのゲームを再利用し、残りだけを実行する。
  - **ビルドが変わったら再開は不可**。新しいビルド + 新しい seeds でラウンド全体をやり直す(§1.4)。
  - **seeds が変わったら再開は不可**(同じラウンドとして扱えない)。
- 再開したラウンドのレポートには「**中断からの再開**」と、**再開時点のビルドコミット・完了済みゲーム数・中断理由**を記録する。
- **中断したラウンドの部分結果を、そのまま主張に使ってはいけない**(50 ゲームに満たないため)。
- 中断の原因が**レフェリーのバグ**だった場合は、そのラウンドは**無効**。原因を直して新しい seeds でやり直す(§7 の「レフェリー自身のバグ」と同じ扱い)。
- 中断の原因が**外部**(電源断・OS 更新・相手プロセスの異常終了)なら、同一ビルド・同一 seeds での再開を許す。

**中断原因の分類は人間が行い、記録する**(機械的に判定できない)。

| 分類 | 扱い | 記録 |
|---|---|---|
| `external` | 再開可 | `round.json` に `resume_cause: "external"` と理由 |
| `referee-defect` | **再開不可(ラウンド無効)** | 原因を修正し、新しい seeds でラウンド全体をやり直す |

- 分類は**再開の時点で**行う(後から結果を見て変えられないように)。
- レポートには「**中断からの再開: N ゲームを再利用、原因 `<reason>`、分類 `external`**」を記録する。
- **中断した時点の部分結果だけを主張に使ってはいけない**。再開して 150 ゲームを完了した結果が主張になる。
- 再開したラウンドのレポートには「**完了した 150 ゲームが主張の対象**であり、中断前の部分結果は単独では主張にならない」旨を明記する。

> 再開を許すのは「同じ測定を続ける」ためであって、「都合の悪い結果を捨てる」ためではない。**ビルドか seeds が変わったら別のラウンド**であり、つなぎ合わせは認めない。

### 1.5 評価 seeds の事前確定手続き

**評価 seeds はラウンド実行前にコミットで確定する。** 確定後にその範囲をチューニングへ使うことを禁止する。

#### 手順(この順序を守る)

1. **範囲を決める**: [`docs/seed-registry.md`](seed-registry.md) の「未使用」範囲から 25 個の連番を選ぶ。**過去に使った範囲と重ならないこと**を台帳で確認する。
2. **コミットする**: `docs/seeds-round-N.md` を作り、seeds の列挙・ラウンド番号・**intetrigence のビルドコミット**・日付を書いてコミットする。**このコミットが「事前確定」の証拠**になる。
3. **台帳を更新して同じコミットに含める**: `docs/seed-registry.md` の該当範囲を「評価(ラウンド N)」として記録する。
4. **実行する**: 確定コミット**以降**のビルドでマッチを実行する。replay header に seeds とビルドコミットが入る。
5. **焼き付ける**: 実行後、台帳の状態を「焼き付き」に更新する。**以後この範囲はチューニングに使わない。**

#### 禁止事項

- 確定した評価 seeds を、重み・パラメータ・評価関数・探索設定の調整に使う
- 評価 seeds の結果を見てから seeds を選び直す
- ラウンド途中で seeds を追加・差し替える
- チューニング用の範囲と評価用の範囲を重ねる
- 台帳に記録せずに seeds を使う

#### `docs/seeds-round-N.md` の形式

```markdown
# Round 1 evaluation seeds

- round: 1
- committed: 2026-11-15
- build: <intetrigence のコミット SHA>   ← このビルドで実行する
- range: 30001-30025
- count: 25
- registry: docs/seed-registry.md(評価(ラウンド 1))
- note: 事前確定。チューニング・診断に使用しない。使用後は焼き付き。
```

- `range:` または `seeds:`(列挙)のどちらでもよい。**`count: 25` を検証する**。
- **`build:` は必須**。実行するビルドを seeds と同時に固定する。
- **順序は「ビルド固定 → seeds 確定 → 実行」**。seeds を先に決めてからビルドを選ぶと、ビルド選択が seeds に依存し得る。
- ランナーは seeds ファイルの**コミットハッシュ**を `round-N.json` に記録する(事前確定の証拠)。

### 1.6 事前スモーク(評価 seeds を焼く前の確認)

ラウンドの前に、**チューニング seeds で短いスモーク**を回してよい。目的は**評価 seeds を消費する前に、桁違いの失敗を検出する**こと。

| 項目 | 推奨 |
|---|---|
| seeds | **チューニング範囲**(例: 9001–9010)。評価 seeds は使わない |
| ゲーム数 | 相手ごとに **10**(10 seeds × 片シート) |
| シート | **A のみ**でよい(過去の敗北が A に偏っているため、A は保守側) |
| turn cap | **公式と同じ 1000**(turn-cap 勝ちの寄与を読むため) |
| 思考時間 | **公式と同じ**(`--ms 100`、8 threads) |
| 出力 | `scripts/evidence/tuning-<opponent>/` など、**評価とは別ディレクトリ** |

**位置づけ**:

- スモークは**診断**であり、**ラウンドの主張に混ぜない**(§1.3 の profile 規律と同じ)。
- スモークの数字は「チューニング seeds 上の参考値」としてラベルを付ける。ラウンドの勝率と合算しない。
- **スモークで 96% を確認することはできない**(n=10 では CI が広すぎる)。検出できるのは「桁違いの失敗」だけ。
- 目安: **10 ゲームで 9 勝未満なら、評価 seeds を焼く前に原因を調べる**。10 勝なら「桁違いではない」と確認できたことになる。
- **スモークは最終ビルドで回す**。ビルドを変えたら再スモークする(古いスモークの結果を持ち越さない)。

#### 焼き付きの記録

`docs/seed-registry.md` に、**範囲・用途・状態(未使用 / チューニング / 評価 / 焼き付き)・使ったラウンド・日付**を記録する。範囲は「使ったら二度と戻さない」。

## 2. ターンと frame

### 2.1 定義

```
turn t = 0, 1, 2, ... 999
frame(t) = t * 12                # 5 PPS、60 fps 固定
```

- 1 turn に**両者が 1 ピースずつ**置く。
- `frame` は**ターン番号から導出**する。実時間は使わない(決定論のため)。
- **実時間のペーシングはしない**(sleep を入れない)。レフェリーはボットの応答を待ち、`think_ms` を記録するだけ。
  - 理由: 両ボットとも 1 手の計算量が固定(intetrigence は `--ms 100`、attax は固定仕事量)なので、ペーシングの有無は**強さに影響しない**。実時間で待つとラウンド(150 ゲーム)の所要時間が伸びるだけで、得るものが無い。
  - 代わりに **1 手 200 ms(= 5 PPS の持ち時間)を超えた手を記録し、レポートに件数を出す**。超過が 0 件なら「公称 5 PPS と実測が一致している」と主張できる。
  - 実時間の制御を入れてもゲーム状態は変わらない(`frame` はターン番号から導出するため)。

### 2.2 ピース供給(プレイヤーごとの袋、同一 seed)

- **各プレイヤーが自分の 7-bag を持つ**。両者の袋は**同じ `piece_seed`** から作る(`Game::new(piece_seed)` を 2 つ)。
- したがって **hold を使うまで、両者の現在ピースと preview は完全に一致する**。
- **hold を使うと、そのプレイヤーの袋だけが 1 個進む**(相手の袋は不変)。以後その 2 人の列は 1 個ずれる。
- hold / preview は各プレイヤーが独立に持つ(s2-spec §2.5 / §2.6)。**hold はターンを消費しない**(1 turn に 1 ピース設置)。

**この設計を採る理由**(v1.1 で「単一の共有袋」から変更した):

1. **TETR.IO と同じ構造**。各プレイヤーが自分のキューを持ち、hold は自分のキューから消費する。
2. **hold が列に影響する**ので、hold の損得が TETR.IO と同じ意味を持つ。共有袋にすると hold が列に影響せず、hold が実質無コストになって TETR.IO より強くなる(評価関数の前提も変わる)。
3. 列のずれは**本人の選択だけ**で決まる。運の非対称は無い。
4. `crates/core` の `Game` がそのまま使える(任意ピースを spawn する API が不要)。

> **実装上の注意**: レフェリーは「この turn のピース」を**プレイヤーごとに自分の袋から**取る。共有の `bag[t]` を配ってはいけない。`crates/core` の `Game::hold()` は「hold が空のときだけ `bag.next_piece()` を呼び、埋まっていれば swap のみ」なので、この意味論と一致する。

### 2.3 1 turn の解決順序

**seat 1 の設置を完全に解決してから、seat 2 の設置を解決する。**

```
for t in 0..1000:
    for seat in [1, 2]:
        piece = プレイヤー(seat) の袋から 1 個(§2.2)
        p = ボット(seat) の着手を取得(§4)
        検証(§4.2)
        設置を適用 → 消去 → 採点 → 相殺 → 送信(§5)
        ゴミ挿入(§5.4)
        if トップアウト: ラウンド終了(§6)
```

**この順序が意味を持つ理由**: seat 1 が turn `t` に送った攻撃は、**同じ turn の seat 2 の相殺で消せる**(キューに入っているため)。逆に seat 2 の攻撃は seat 1 の同じ turn の相殺には間に合わない。つまり **seat 2 がわずかに有利**。シートの入れ替えでこの有利を相殺する。

> 相殺は到着(frame)を見ない(s2-spec §7.3)。キューにあるものは全部削れる。20 frame の遅延が効くのは**挿入**だけ(§5.4)。

### 2.4 決定論モード(`--deterministic`)の扱い(2026-11-16 決定)

`crates/bot` に**決定論モード**がある(`SearchConfig.deterministic`)。**deadline チェックをせず、固定の `(depth, width)` を 1 回だけ実行する**ので、スレッド数にも実行時間にも依存しない。

**決定論モードはチューニング専用。公式ラウンドでは使わない。**

| 用途 | モード | 理由 |
|---|---|---|
| **A/B 比較・重みの掃引** | **決定論** | 時間のばらつきが消え、**変えた 1 つ以外が動かない** |
| **公式ラウンド** | **anytime(`--ms 100`)** | goal が「**思考 100ms**」を条件にしている。決定論は時間制約を外すので**条件が変わる** |

**例外**: 決定論モードの固定 `(depth, width)` が **p99 で 100 ms 未満**に収まるなら、公式ラウンドでも使ってよい。ただし:

- **レポートに「決定論モード、固定 depth=D / width=W、実測 p99 = X ms」と明記**する
- **`--ms 100` を使った場合との強さの比較**を 20 ゲーム以上で示す

> **チューニングと公式でモードが違う危険**: 決定論で選んだ重みが **anytime で最適とは限らない**。これは「**探索が動かない前提で重みを校正した**」失敗(v1.3.17 §6.9)と**同じ種類**。**最終確認は必ず公式と同じモードで行う**。

**§8.4.1 との関係**: 決定論モードでは `fallback` は常に `false`、`depth` / `width` は固定。**記録は必要**(「探索した」ことの証明として有効)。ただし **`fallback` 率は 0 になるので、anytime モードの指標と混ぜない**。

**arena 側の要求**: `--deterministic` フラグを追加し、**レポートに決定論モードかどうかを記録**する。**混在したラウンドは無効**(§8.3.1)。

#### 2.4.1 実測: 決定論の方が**深く探索でき、かつ 100ms に収まる**(2026-11-16)

`garbage-pressure` プロファイル、300 手、8 スレッド、release ビルドでの実測(bot-dev):

| スケジュール | median | p99 | max | 100ms 超 |
|---|---|---|---|---|
| d4 w96 | 15.4 | 28.4 | 30.0 | 0 |
| d8 w96 | 32.3 | 37.9 | 46.9 | 0 |
| d8 w192 | 63.3 | 77.2 | 86.9 | 0 |
| **d8 w256** | 83.0 | 105.9 | 116.2 | **5** |
| **d10 w128** | **55.9** | **66.9** | **69.8** | **0** |
| **d12 w128** | 68.7 | 89.0 | 108.7 | **1** |

**anytime(`--ms 100`)は depth 4.4 / width 138 で頭打ち**。**`d10 w128` は depth 10 で、anytime の 2.3 倍深い。**

**したがって §2.4 の例外が適用できる**: `d10 w128` は **p99 66.9 ms / max 69.8 ms** で **100 ms 未満**。

| 判断 | 内容 |
|---|---|
| **公式ラウンドのモード** | **決定論 `d10 w128` を使ってよい** |
| **条件** | レポートに「決定論、固定 depth=10 / width=128、実測 p99 = 66.9 ms / max = 69.8 ms」と明記 |
| **条件** | `--ms 100`(anytime)との**強さの比較を 20 ゲーム以上**で示す |
| **条件** | **`official` プロファイルでも同じ計測をやり直す**(下記) |

**`100 ms` は上限であって目標ではない。** 56 ms で打つのは条件違反ではなく、**むしろ速い**。

#### 2.4.2 `official` プロファイルでは `d10 w128` は使えない(2026-11-16 実測)

**`garbage-pressure` の計測は公式に使えなかった。** `official`(空の盤面)で測り直した結果(bot-dev、400 手):

| スケジュール | median | p99 | **max** | **100ms 超** | 余裕 |
|---|---|---|---|---|---|
| d4 w128 | 19.5 | 30.7 | 47.8 | 0 | 52 ms |
| d6 w96 | 26.8 | 83.0 | **118.2** | **2** | **✗** |
| **d6 w128** | 32.0 | 52.0 | **56.0** | **0** | **44 ms** |
| **d8 w96** | 35.6 | 63.5 | **83.0** | **0** | **17 ms** |
| d8 w128 | 47.1 | 100.5 | **131.9** | **4** | **✗** |
| **d10 w128** | 58.1 | 108.6 | **131.0** | **6** | **✗** |
| d10 w160 | 79.4 | 172.7 | 235.4 | 58 | ✗ |

**空の盤面は候補が多く、`garbage-pressure` より 1.9 倍遅い**(`d10 w128` の max 69.8 → 131.0)。

**判定基準は `max`**(1 手でも 100 ms を超えたら条件違反)。したがって:

| スケジュール | 判定 |
|---|---|
| `d10 w128` | **✗**(max 131.0、6 手超過) |
| `d8 w128` | ✗(max 131.9、4 手超過) |
| `d8 w96` | **△**(max 83.0、余裕 17 ms) |
| **`d6 w128`** | **○**(max 56.0、余裕 44 ms) |

**400 手は 10,000 手(50 ゲーム × 200 turn)の 4%** にすぎない。**max はサンプル数とともに伸びる**ので、**17 ms の余裕は足りない**。**`d6 w128` が安全**。

#### 2.4.3 **本質は「anytime のランプ順」** — 修正すれば決定論に頼らなくてよい

**決定論が anytime より深い理由は、anytime の width ランプ(96→768)が浅い反復で予算を使い切るから**。**anytime 自体が弱いのではない。**

**したがって推奨は「固定スケジュールを選ぶ」ではなく「anytime のランプを depth 優先に変える」**:

```
現行: depth 4 で width 96 → 192 → 384 → 768 → …(幅を先に広げる)
推奨: depth 4 w96 → depth 6 w96 → depth 8 w96 → depth 10 w96 → depth 10 w128 → …
      (深さを先に上げる)
```

**これで得られるもの**:

| 性質 | 内容 |
|---|---|
| **通常の手** | `d10 w128` 相当(median 58 ms)まで到達 |
| **重い手** | 期限で打ち切り、**完了した最深の反復**(depth 8 など)を返す |
| **時間** | **100 ms を超えない**(anytime の保証) |
| **protocol の例外** | **不要**(anytime モードのまま) |

**固定スケジュールより厳密に優れる**: **同じ深さを通常時に得ながら、裾で死なない。**

**要求**: **anytime のランプ順を depth 優先に変更**し、`d10 w128` 相当の深さに届くか測る。**届けば決定論は不要**(チューニング用に残す)。

#### 2.4.4 **depth 優先 anytime は実測で失敗した** — 決定論 + 強制打ち切りが正解

v1.39 で「anytime のランプを depth 優先にすれば決定論に頼らずに済む」と書いたが、**実測で否定された**(bot-dev、`official`、400 手):

| 上限 | median | p99 | **max** | **100ms 超** | **depth p50 / p90 / max** |
|---|---|---|---|---|---|
| d12 w96 | 96.8 | 105.8 | **123.1** | **12** | **6** / 7 / **8** |
| d12 w128 | 96.9 | 111.x | — | — | — |

**anytime は depth 6(p50)で頭打ち**。**決定論 `d8 w96` は depth 8 を毎手保証し、max 83.0 ms / 100ms 超 0/400。**

**失敗の理由**: **anytime の deadline チェックが「レベル間」だけ**。**1 レベルが 20 ms 以上かかると、期限を 5 ms 過ぎていても次のレベルに入ってしまう。** レベル内でチェックしない限り、anytime は**上限を保証できない**。

**したがって公式は決定論 `d8 w96`**。

#### 2.4.5 **強制打ち切り(安全弁)を必須にする**

**決定論は構造的に時間を保証しない。** 400 手で max 83.0 ms でも、**10,000 手(50 ゲーム × 200 turn)では max が伸びる**。**83 → 100 ms は 20% の伸びで到達する**。

**要求**: 決定論モードに**ハード期限(95 ms)を入れ、超えたら打ち切って「完了した最深の反復」を返す**。

| 性質 | 内容 |
|---|---|
| **通常の手** | 固定 `(depth, width)` を完走(決定論) |
| **重い手** | 95 ms で打ち切り、**完了した最深の反復**を返す |
| **時間** | **95 ms を超えない**(測定のオーバーヘッド 5 ms を残す) |
| **記録** | **手ごとに `aborted`(bool)を記録**する |

**レポートの扱い**:

| 状況 | 記載 |
|---|---|
| **50 ゲームで `aborted` が 0** | **「決定論 `d8 w96`、max X ms、打ち切り 0」**と書ける。**ラウンドは決定論** |
| **`aborted` が 1 以上** | **打ち切り件数と、打ち切った手の depth 分布**を書く。**「決定論」とは書かない** |

**§8.4.1 との整合**: `fallback = (iterations == 0)` なので、**95 ms で打ち切っても 1 レベル以上完了していれば `fallback = false`**。**`fallback` と `aborted` は別の指標**。

#### 2.4.6 **決定論と時間上限は本質的に両立しない** — 「打ち切り 0 なら決定論」で運用する

**逐次固定は性能を破壊した**(bot-dev、`official`、400 手):

| スケジュール(逐次) | median | max | 100ms 超 | **aborted** |
|---|---|---|---|---|
| d4 w128 | 68.8 | 88.3 | 0 | **0** |
| d6 w128 | 95.6 | 96.7 | 0 | **400** |
| **d8 w96** | 95.6 | **100.8** | **1** | **400** |

**`d8 w96` は逐次では 1 手も完走できない**(400/400 が打ち切り)。**並列版の max 83.0 ms は、ワーカーの期限チェックによる早期打ち切りを含んだ数字**だった。

**構造的な緊張**:

| 要求 | 必要なこと | 矛盾 |
|---|---|---|
| **決定論** | **時刻に依存する判断をしない** | — |
| **時間上限** | **時刻に依存して打ち切る** | **決定論を壊す** |

**一般には両立しない。** したがって**「打ち切りが 0 なら決定論」という運用**にする(§2.4.5)。

**設計**:

1. **決定論モードでは、ワーカーの期限チェックを外す**(子の集合が入力 beam だけで決まる)
2. **打ち切りは「レベル境界」だけで行う**(95 ms)
3. **`aborted` を手ごとに記録**
4. **ラウンド全体で `aborted == 0` なら「決定論」と主張できる**

**残る危険**: **ワーカーのチェックを外すと、1 レベルの所要時間が伸びる**。**レベル境界の打ち切りは、レベルの途中を止められない。**

**したがって必須の測定**:

| 測るもの | 合格条件 |
|---|---|
| **1 レベルの最大所要時間**(ワーカーチェックなし) | **95 ms 未満**。超えるなら、そのレベルは打ち切れずに上限を破る |
| `d8 w96` の max / `aborted` | `aborted == 0` が望ましい。多いならスケジュールを下げる(`d6 w128` / `d8 w64`) |

**もし 1 レベルが 95 ms を超えるなら、そのスケジュールは使えない。** **`d8 w96` を諦めて `d6 w128` に落とす**か、**レベル内にも粗いチェック(チャンク境界)を入れて決定論を部分的に犠牲にする**かの選択になる。**後者を選ぶなら「決定論」とは書かない。**

#### 2.4.7 **打ち切りは「95 ms」ではなく「100 − 1 レベルの最大時間」にする**

**レベル境界の打ち切りは、レベルの途中を止められない。** したがって実際の上限は:

```
実際の上限 = 打ち切り時刻 + 1 レベルの最大所要時間
```

**実測(2026-11-16、並列決定論、`official`、400 手)**:

| スケジュール | median | p99 | **max** | 100ms 超 | **aborted** |
|---|---|---|---|---|---|
| d4 w128 | 17.5 | 22.7 | 29.6 | 0 | **0** |
| d6 w96 | 23.9 | 57.0 | 93.8 | 0 | 2 |
| **d6 w128** | **30.7** | 47.5 | **51.4** | 0 | **2** |
| **d8 w96** | — | — | **98.9** | 0 | **3** |

**`d8 w96` の max 98.9 は「95 ms で打ち切った後に、そのレベルが 3.9 ms 走った」結果。** **95 ms は上限ではない。**

**要求**:

| 項目 | 内容 |
|---|---|
| **測る** | **1 レベルの最大所要時間**(`max_level_time`) |
| **打ち切り時刻** | **`100 ms − max_level_time − 5 ms`**(余裕 5 ms) |
| **検算** | **`打ち切り時刻 + max_level_time <= 95 ms`** を満たすこと |

**例**: `max_level_time = 15 ms` なら **打ち切りは 80 ms**。**`d8 w96` の median 30.7 ms なら、通常の手は 80 ms で十分に完走する。**

**`d6 w128` は max 51.4 ms で、打ち切り 95 ms に対して余裕 44 ms。** **`aborted` 2/400 は「レベルの途中で 95 ms に達した」ケース**で、**打ち切りを 80 ms に下げると増える**可能性がある。**`d6 w128` は 95 ms のままでよい**(max が 51.4 なので 95 ms に届かない)。

#### 2.4.8 **思考時間は機械の専有なしには測れない**(2026-11-16)

**同じスケジュール・同じ 400 手で、max が 3 倍変わった**(bot-dev、`official`):

| 回 | median | p99 | **max** | 100ms 超 | aborted |
|---|---|---|---|---|---|
| 1 回目(機械が空いていた) | 29.2 | 35.6 | **37.2** | 0 | 2 |
| 2 回目(他の測定と同時) | 33.4 | 85.4 | **111.9** | **2** | 2 |

**`d6 w128` の max は 37.2 ms でも 111.9 ms でもあり得る。** **差はボットではなく機械の負荷。**

**これは「思考 100 ms」の主張の根拠を壊す。** `think_ms` はレフェリーが測る**実時間**なので、**機械の負荷とボットの計算量が区別できない**。

**したがって要求する**:

| # | 要求 |
|---|---|
| 1 | **思考時間の測定は機械を専有して行う**(他の測定・ビルド・テストを同時に走らせない) |
| 2 | **公式ラウンドも機械を専有して実行する** |
| 3 | **レポートに「専有で実行した」と明記**する。専有できなかった場合は**その旨と、同時に走っていたもの**を書く |
| 4 | **`think_ms` が 100 ms を超えた手があれば、件数と最大値を報告**する(§8.4) |

**負荷に強いスケジュール**(実測、2 回とも安定):

| スケジュール | max(2 回) | aborted | 判定 |
|---|---|---|---|
| **d4 w128** | 32.3 / 29.6 | **0** | **負荷に強い**。ただし depth 4 |
| d6 w96 | 45.9 / 72.9 | 2 | 比較的安定 |
| **d6 w128** | 37.2 / **111.9** | 2 | **負荷に弱い** |
| d8 w96 | 105.5 | 3 | **不適** |

**判断**:

- **機械を専有できるなら `d6 w128`**(depth 6、max 37.2)
- **専有できないなら `d4 w128`**(max 32.3、aborted 0)。ただし **depth 4 は anytime の p50 6 より浅い**
- **`d8 w96` は使わない**(105.5、100 ms 超)

**注意 3 点**:

1. **この計測は `garbage-pressure` プロファイル**。**公式は `official`(空の盤面)**なので、**同じ計測を `official` でもやる**こと。盤面が違えば探索コストも違う
2. **`d12 w128` は 1 手だけ 100 ms を超える**。**`d10 w128` を上限**とする
3. **決定論は anytime ではない**ので、**病的な盤面で 100 ms を超える可能性は残る**。**レフェリーの `think_ms` で監視**し、**超過があれば記録**する(§8.4)

## 3. ラウンド進行

### 3.1 状態

各プレイヤーが持つ状態(s2-spec §9 のとおり):

```
board, combo, b2b_streak, pieces_placed, sent_total,
garbage_queue, garbage_rng, last_column, has_changed_column,
hold, hold_available, next[5]
```

レフェリーが追加で持つもの:

```
turn, frame, seed, sheet, seat_of[slot], log(§8)
```

### 3.2 擬似コード

```
fn run_round(seed, sheet) -> RoundResult:
    d = derive_seeds(seed)                       # s2-spec §11-U7
    players = [Player::new(d.piece_seed, d.garbage_seeds[0]),   # slot 0 = intetrigence
               Player::new(d.piece_seed, d.garbage_seeds[1])]   # slot 1 = attax
    order = match sheet { A => [0, 1], B => [1, 0] }            # seat 順

    for t in 0 .. 1000:
        frame = t * 12
        for slot in order:                        # seat 1 → seat 2
            piece = players[slot].bag.next_piece()        # 各自の袋(§2.2)
            move = ask_bot(slot, snapshot(slot, piece))   # 応答を待つ(時間制限なし)
            verify(slot, move, piece)             # §4.2
            apply(slot, move, frame)              # §5
            if topped_out(slot): return result(slot)
    return timeout_result()                       # §6.3
```

## 4. 着手の提出と検証

### 4.1 提出形式

ボットは「どのピースを、どの回転で、どの位置に、hold を使ったか」を返す。TBP では `suggestion` の `moves` 配列(優先順)で届く(attax-integration §5.3)。

**レフェリーが要求する最小情報**:

| フィールド | 意味 |
|---|---|
| `piece` | 置くピース種(hold 使用時は hold されていたピース) |
| `rotation` | 0..3(SRS 状態。0 = spawn) |
| `x`, `y` | **バウンディングボックス左下**(s2-spec §2.2.1 と同じ基準点) |
| `hold` | その turn で hold を使ったか |

> **座標の基準点は「ボックス左下」で固定**。回転中心や最下段セルではない。`crates/core` の `Board::spin_type` / `t_spin_corners` もこの基準点を取る。

### 4.2 検証(拒否したらそのゲームは forfeit、§7)

1. **合法性**: セルが `0 ≤ x ≤ 9` / `0 ≤ y ≤ 39`、既存ブロックと重ならない。
2. **接地**: 1 行下に動かせない(空中で止めていない)。
3. **到達可能性**: `crates/bot` の movegen で spawn から到達できること(PLAN §3.3 の監査)。
4. **hold の整合**: hold を使ったなら `hold_available` が真で、ピースが hold の中身と一致。
5. **スピンラベル**: ボットの主張は**採用しない**。レフェリーが再計算する(s2-spec §4)。規則は §4.2.1。

> 3 は計算コストが高い。**本番では 1 ゲームおきに検証**し、全ゲームは replay 検証(§8.3)で担保する運用でもよい。ただし**拒否 0 件を記録**すること。

### 4.2.1 スピンラベルの決定規則(最大スピン)

**同じセル集合に複数の経路で到達できるとき、スピンラベルは「到達可能な経路のうち最強のもの」を採る**(`none` < `mini` < `full`)。

```
spin(cells) = max over paths p reaching cells of spin_type(cells, last_action(p), kick(p))
```

- **理由**: 本プロトコルはボットから**セル集合**を受け取り、キー列は受け取らない(TBP の `suggestion` にキー列が無い)。経路が不明な以上、決定的な規則が要る。
- **`last_action(p)`**: その経路の最後の操作が回転か(s2-spec §4.1)。回転で終わる経路が 1 本でもあればスピン候補になる。
- **`kick(p)`**: 5th kick を使ったか(s2-spec §3.3)。TST/FIN の昇格は経路依存。
- **実行する経路**: レフェリーは**最大スピンを達成する経路**を 1 本選んで `Game::apply` で再生する。最大スピン同士の経路のどれを選んでも**盤面と採点は同一**なので、同ラベル内の選択は実装依存でよい(ただし決定的であること)。
- **実装**: `crates/core` の movegen と `crates/arena` の movegen が同じ規則を実装している(BFS で各セル集合に対し最大スピンを保持)。

> **TETR.IO より寛容であることを明記する**: 実機では「実際に回して置いたか」で決まるが、本プロトコルは「回して置けたなら回したとみなす」。したがって**回転せずに置いた配置でもスピンとして採点され得る**。両者に同じ規則を適用するので公平ではあるが、TETR.IO のスコアと一致しない。レポートではこの点を明記すること。

> **落とし穴**: セル集合に畳むとき「最初に見つかった経路のラベル」を残すと、I/S/Z のように 180° 対称で同じセルを複数経路が持つピースで **`mini` を落とす**。必ず**最大**を残す。

### 4.3 第 1 候補の採用

TBP の `moves` は優先順に並ぶ。レフェリーは**先頭から走査し、自前の合法手集合に入る最初のもの**を採用する(attax-integration §8-D3)。

- 採用したインデックスを記録する(0 なら「第 1 候補採用」)。
- **第 1 候補採用率**を毎ゲーム記録(PLAN §3.3)。attax が 1.0 でない場合、その理由を残す。

## 5. 1 設置の解決

順序は **s2-spec §6.8 の擬似コードに完全に従う**。レフェリーが独自解釈をしてはいけない。

### 5.1 手順

```
1. ピースを盤面に置く
2. ライン消去を判定(lines, g_cleared)
3. スピン判定(spin)を §4.2-5 のとおり再計算
4. パーフェクトクリア判定(pc)
5. compute_attack(lines, spin, combo, b2b_streak, pc, g_cleared, multiplier(frame))
   → events(送信イベント列)
6. events を順に相殺(§5.2)
7. 残りを相手のキューへ送る(§5.3)
8. ライン消去なしなら、自分のキューから挿入(§5.4)
```

### 5.2 相殺

**イベントごとに** `GarbageQueue::cancel_with_opener(amount, opener)` を呼ぶ(s2-spec §7.3 / §7.4)。

- イベントの順序は `compute_attack` が返す順(surge → 通常攻撃 → PC)。
- `sent_total` は「実際に相手へ飛んだ行数」を累積する(相殺で消えた分は含まない)。
- Opener Phase の判定は `pieces_placed + 1 <= 14` かつ `queue_total >= sent_total`(s2-spec §11-U5)。

### 5.3 送信

残った行数を**1 パケット**として相手のキューに積む:

```
opponent.garbage_queue.receive(remaining, arrival_frame = frame)
```

- `arrival_frame` は**送信した turn の frame**(= `12t`)。
- イベントが複数あった場合、**イベントごとに別パケット**にする(s2-spec §7.2)。合算してはいけない。
- 送信量 0 のイベントはパケットを作らない。

### 5.4 挿入

`lines > 0` なら挿入しない(combo blocking)。`lines == 0` なら:

```
holes = self.garbage_queue.take_insertable(0, frame)   # 最大 8 行、arrival+20 <= frame
self.board.insert_garbage(&holes)                      # 穴の縦順は s2-spec §7.5
```

- **`take_insertable` が返す順序 = 挿入順**。`holes[0]` が**最上段**になる(s2-spec §7.5 の検算例)。
- 遅延: turn `t` に送られたパケットは `frame >= 12t + 20` で挿入可能 → **turn `t+2` 以降**(s2-spec §11-U9)。

**TBP への反映(`start` 再送)**: 挿入が起きたら、そのプレイヤーのアダプタに **`start` を再送**して盤面を同期させる(attax-integration §8-E1)。

- **挿入しなかった場合は再送しない**(combo blocking で `lines > 0`、または due なパケットが無い)。盤面は `play` で既に同期している。
- **forfeit / ラウンド終了時は再送しない**(ゲームが終わっている)。
- ゴミは**自分のロック時にしか自分の盤面に入らない**(§5.4)ので、相手の turn 中に盤面が変わることはない。再送のタイミングは「自分のロック直後」だけでよい。

## 6. 終了条件と勝敗

### 6.1 トップアウト

- 死亡条件は **block-out のみ**(s2-spec §2.3)。lock-out は無い。Clutch Clear は有効。
- 自分の設置を解決した後に、次のピースの spawn が衝突するかで判定する。
- **どちらかがトップアウトした瞬間にラウンド終了**。その turn の残りの設置は行わない。トップアウトした側の負け、相手の勝ち。
- したがって **「同一 turn で両者がトップアウト」は起こらない**(先に死んだ側で打ち切るため)。**S2 に引き分けは存在しない**。勝者が決まらないのはターン上限(§6.3、未決着)と forfeit(§7、不成立)の 2 つだけで、どちらも `winner = None`。

> **公平性の注意**: 解決順が seat 1 → seat 2 なので、**seat 1 が先に死ねば seat 2 はその turn を打たずに勝つ**。これは逐次解決に固有の非対称で、シートの入れ替え(§1.2)で相殺する。1 ゲーム単位では偏るが、50 ゲームでは各ボットが 25 回ずつ両方の席を経験する。

### 6.2 引き分け・未決着の扱い

**S2 に「引き分け」は無い**(§6.1 のとおり、同一 turn の両者トップアウトは起こらない)。

我々のプロトコルには **2 種類の「勝者が決まらない結果」** があり、**混同してはいけない**:

| 種類 | 発生条件 | `winner` | 勝ちに数えるか |
|---|---|---|---|
| **未決着**(`unresolved`) | ターン上限に到達(§6.3) | `None` | 数えない |
| **不成立**(`no contest`) | forfeit(§7) | `None`(v1.26 以降。§7.1.3) | 数えない |

どちらも**勝ちに数えない**。段階 1・2 は `wins_topout == 50`(未決着・不成立は 0 件)、段階 3 は `wins_topout >= 48` かつ `turncap == 0`(§1.4)。**未決着・不成立が 1 件でも出たら段階 1・2 は不通過**。

> **v1.25 までの誤り**: 「引き分けは勝ちに数えない。段階 1 は `wins == 50`」と書いていたが、§1.4 の段階ゲートと矛盾していた(当時の表記は ≥45/50、v1.27 で `wins_topout == 50`)。また実装の `draws` は `winner.is_none()` で、**未決着と引き分けを混同**していた(`docs/s2-rule-audit.md` F2)。

### 6.3 ターン上限(1000 turn)

1000 turn を終えてもトップアウトしなければ、**未決着**(`winner = None`, `reason = "TurnCap"`)として記録する。

> **v1.25 までの誤り**: 「累計受信ゴミ行数が少ない方の勝ち → 同数なら累計送信行数が多い方の勝ち」という**順位付けで勝者を決めていた**。これは **TETR.IO にも我々のルールにも存在しない、我々が発明した規則**だった。実装(`referee.rs`)からは削除済み。**攻撃量・被ゴミ量で勝者を決めてはいけない** — それは「ルール上の勝敗」ではなく「指標の比較」であり、レポートでは `received_total` / `sent_total` を**参考指標として併記するだけ**にする。

1000 turn = 200 秒(5 PPS)。両者が生き残ることはまれだが、起きた場合は**未決着として報告する**(勝ちに数えない)。

### 6.4 記録する結果

```
RoundResult {
    winner: Option<slot>,        // None = 未決着(TurnCap) または 不成立(Forfeit)
    reason: TopOut | TurnCap | Forfeit | Stuck,
    turns: u32,
    final_frame: u64,
    per_player: { sent_total, received_total, attack_events, max_combo, max_b2b, surge_released },
}
```

- `reason = "Stuck"` は「合法手なし」で、**S2 の top-out ではない**(到達不能。`docs/s2-rule-audit.md` F1)。集計では未決着扱いにする。
- `winner` が `None` のとき、`reason` で未決着と不成立を区別する。**`draws` という名前でまとめない**(F2)。

## 7. エラーと forfeit

| 事象 | 扱い |
|---|---|
| ボットの応答が返らない | **待つ**(時間制限なし)。ただし `--timeout` を超えたら forfeit(既定 30 秒) |
| 非合法な着手を返した | **そのゲームは forfeit**。理由と盤面・着手を記録 |
| **候補が空**(`suggestion` に合法手が無い) | 下の「空の候補」を参照 |
| プロセスが異常終了 | forfeit。stderr を保存(attax-integration §8-A5) |
| プロトコル違反(JSON 不正・必須フィールド欠落) | forfeit。理由を記録 |
| レフェリー自身のバグ(不変条件違反) | **マッチ全体を中断**。ゲームを無効として記録し、原因を修正して再実行 |

**空の候補(`suggestion` が空)の扱い**: レフェリーは**自分の movegen でも合法手を列挙して**から決める。

| レフェリーの movegen | 意味 | 扱い |
|---|---|---|
| 合法手が**ある** | ボットの movegen が壊れている | **forfeit**(ボットの失敗) |
| 合法手が**無い** | 盤面が詰んでいる(置ける場所が無い) | **トップアウト**(盤面の責任。相手の勝ち) |

- 両者は勝敗が同じでも**記録の意味が違う**。forfeit は「ボットが失敗した」、トップアウトは「盤面が死んだ」。レポートで混ぜないこと。
- `Game::is_over()`(次 spawn の衝突)だけでは「置ける場所が無い」を検出できないため、この 2 段判定が要る。

> **`NoMoves`(合法手が無い)は実戦では到達しない**(§6.1 の「同時トップアウト」と同じ扱い)。
>
> **証明**: 生きている active ピースは、定義上 spawn から到達可能である(プレイヤーの入力でそこに来た)。接地していればそのまま接地済みの到達可能配置であり、接地していなければ soft drop した状態が到達可能な接地配置になる。よって **`is_over() == false` なら movegen は必ず 1 個以上返す**。
>
> したがって `NoMoves` は「active が存在しない / 盤外」の**防御分岐**であり、その状況では `is_over()` が先に真になる。テストとして構成できないので、コードに理由コメントを残して分岐を保持する(将来 movegen の前提が変わったときの保険)。

**1 設置につき `suggest` は 1 回だけ**。リトライしない(リトライすると `think_ms` の意味が壊れ、公平性も崩れる)。

- forfeit の扱いは **§7.1 で決定済み**(勝ちとして数え、`reason` と `forfeit_cause` で内訳を出す)。ここには重複して書かない。
- **レフェリーのバグで無効になったゲームは、seed を再利用して再実行する**(結果を見てから seed を選ぶことはしない)。

### 7.1 forfeit の扱い(決定、v1.21 改訂)

**決定**: forfeit は**ゲームの裁定としては相手の負け**だが、**勝ち(実力の証明)には数えない**。勝ちに数えるのは `TopOut` と `TurnCap` だけ(§7.1.3)。

#### 7.1.1 なぜ「裁定」と「勝ち」を分けるか

- レフェリーは「相手が合法手を返さない」以上、ゲームを続行できない。**裁定は相手の負け**しかない(ここは変えない)。
- しかし forfeit は**相手の実装制約**(視野 20 行)によるもので、**我々が相手を潰したわけではない**。これを勝ちに数えると、**相手のアダプタ故障率を勝率として報告する**ことになる。
- そこで **裁定(ゲームの決着)と主張(実力の証明)を分ける**。ゲームは機械的に終わらせ、**主張には `TopOut` と `TurnCap` だけを使う**。
- 分母は固定する(50 ゲーム)。**勝ちの種類で分母を変えない**ので、恣意的な集計にはならない。

#### 7.1.2 内訳の記録(必須)

各ゲームに `winner` と `reason` を記録する。

| `reason` | 意味 |
|---|---|
| `TopOut` | 盤面が死んだ(block-out)。**ルール上の決着** |
| `Forfeit` | 相手が合法手を返さなかった。**相手の実装制約による決着** |
| `TurnCap` | 1000 turn 到達。**未決着**(`winner = None`)。§6.3 |
| `Stuck` | 合法手なし。**S2 の top-out ではない**。到達不能。`winner = None`(`docs/s2-rule-audit.md` F1) |

さらに `Forfeit` は**原因で分類する**:

**判定は 1 条件だけ**(候補 0 を受け取った時点で評価。`V` = 相手の宣言可視高):

```
referee_moves = レフェリーの movegen(現在ピース + hold)
visible_moves = { m ∈ referee_moves | m の全セルが row 0..V-1 に収まる }

if visible_moves が空   → forfeit-vision   (相手の視野では表現できない)
else                   → forfeit-other    (表現できるのに 0 候補 = アダプタ故障)
```

| `forfeit_cause` | 判定 | 意味 |
|---|---|---|
| `vision` | `visible_moves` が空 | 相手の視野制約による(attax は 20 行) |
| `other` | `visible_moves` があるのに 0 候補 | **アダプタ故障**(相手の movegen が壊れている) |
| `unknown` | `V` が不明 | `vision` と混ぜない |

> **2026-11-14 修正(重要)**: v1.9〜v1.20 は「active ピースの最下セル行 >= `V`」を条件に含めていたが、**S2 の spawn は row 20〜21 なので `V = 20` の相手に対して常に真**になり、**全 forfeit が vision に化けていた**。この条件は削除した。
>
> **使ってはいけない条件**:
> - `active` の最下セル行 >= `V`(常に真になる)
> - スタック上端 >= `V`(十分条件ですらない。スタックが 20 行に達しても、可視行に収まる配置が存在し得る)
>
> **正しい判定は「可視行に完全に収まる合法配置があるか」だけ**。

- 相手の宣言した可視高は**ボット記述に含める**(`visible_rows`。attax = 20、intetrigence = 40)。
- スタック上端は、候補 0 を受け取った時点の盤面から計算する。

#### 7.1.3 勝ちの定義(2026-11-14 改訂)

**勝ちに数えるのは `TopOut` と `TurnCap` だけ。**

| 決着 | 勝ちに数えるか | 理由 |
|---|---|---|
| `TopOut`(相手が潰れた) | **数える** | 実力の証明 |
| `TurnCap`(§6.3 の未決着) | **数えない** | 勝負がついていない。`winner = None`(v1.26 改訂)。**全段階で 1 件でも不通過** |
| `Forfeit`(vision) | **数えない** | 相手の視野制限による**不戦**。実力の証明ではない |
| `Forfeit`(other) | **数えない** | ゲーム自体が無効(§7.1.2) |
| `Stuck`(合法手なし) | **数えない** | S2 の top-out ではない。到達不能(`docs/s2-rule-audit.md` F1) |

> **v1.26 改訂**: `TurnCap` を「勝ちに数える」から「数えない」に変更した。理由: 実装が `winner = None` を返すようになり(未決着)、**勝ちに数えるには `winner` を `Some(0)` にする必要がある**。1000 turn を両者が生き延びたゲームは「勝負がついていない」のであって、勝ちではない。`wins_turncap` は常に 0 になる。
>
> **代替案(却下)**: `TurnCap` を「生存勝ち」として `winner = Some(0)` にする。これは**プロトコル上の発明**であり、「50 勝 0 敗」の主張に未決着を混ぜることになるため却下した。

**これは 2026-11-14 の重大な修正**。旧定義は forfeit を勝ちに数えていたため、**相手のアダプタ故障率を勝率として報告していた**(attax 相手の 220 ゲームで forfeit-vision 194、実際の `TopOut` 勝ち 0、`TurnCap` 勝ち 13 → **実質 5.9%**)。

#### 7.1.3.1 `winner` の記録規則(v1.26)

**「裁定」と「`winner` フィールド」と「勝ちの集計」は 3 つとも別物**。混同すると記録と主張が食い違う。

| 決着 | `winner` | 勝ちの集計 | 備考 |
|---|---|---|---|
| `TopOut` | `Some(勝者)` | **数える** | 唯一の「実力の証明」 |
| `TurnCap` | **`None`** | 数えない | 未決着 |
| `Forfeit` | **`None`** | 数えない | 不成立(no contest) |
| `Stuck` | `None` | 数えない | 到達不能 |

> **v1.26 改訂**: `Forfeit` の `winner` を `Some(相手)` から **`None` に変更**した。理由: forfeit は**相手の実装制約**であり、TETRA LEAGUE の切断(プレイヤーの意思・回線)とは性質が違う。ゲートが forfeit を勝ちに数えていない以上、`winner` だけ `Some(相手)` にすると**記録と主張が食い違う**(`docs/s2-rule-audit.md` F5)。
>
> **TETRA LEAGUE との差**: TETRA LEAGUE では切断は負け。我々の forfeit は「相手が合法手を返せない」であり、切断ではない。**この差はレポートで開示する**(§8.5)。

#### 7.1.3.2 プロセスの終了(プロセス死、2026-11-16 追加)

- 相手プロセスの終了(stdout の EOF)は `forfeit`(`cause = other`)として
  **no contest**(`winner = None`)で記録する。勝ちにも負けにも数えない。
- **再起動・リトライはしない**。盤面・RNG・コンボが失われた後の続行は
  **別ゲーム**であり、同じゲームとして数えるのは forfeit を勝ちに数えるのと
  同じ種類の誤りである。
- **分母は常に 50**。不成立ゲームを除いた勝率は計算しない(§7.1.1)。
- 段階 1(CC2)・段階 2(clys)は `no_contest == 0` を要求する。**1 件でも
  出れば不通過**。
- clys 戦は常に `CLYS_TBP_LOG` を有効にし、プロセス死の exit code/signal を
  記録する(次回の原因特定のため)。stderr は空のことが多い。

#### 7.1.4 レポート要件(必須)

1. **決着を種類別に分けて出す**: `wins_topout` / `losses_topout` / `unresolved`(TurnCap)/ `no_contest`(Forfeit)/ `stuck`。`no_contest` は `forfeit_vision` / `forfeit_other` / `forfeit_unknown` に割る。**合計だけを出してはいけない。`draws` という名前を使わない。**
2. **勝率は `TopOut` の勝数で計算する**。`TurnCap` は未決着で勝ちに数えない
   (v1.26)。`forfeit-vision` を勝ちに含めた数字を「勝率」として出してはいけない。
3. **`forfeit-vision` は件数と理由を別掲**する(ゲート外)。「相手の視野制限により N ゲームが不戦」と書く。
4. **`forfeit-other` が 1 件でもあればラウンド不成立**。原因を修正して新しい seeds でやり直す(§7.1.2 のアダプタ故障)。
5. **フル視野相手の推定**を出したいなら、`TopOut` で決着したゲームのみの勝率を別掲し、n と Wilson CI を併記して「参考値」と明記する。

### 7.2 S2 非対応ボットの採点オーディット(CC2 / clys)

CC2 と clys は **S2 非対応**(guideline 採点)なので、彼らの申告する攻撃値は我々の S2 採点と一致しない。扱いは attax と同じ。

- **レフェリーが常に再計算する**。ボットの申告値(あれば)は `declared_attack` として記録するだけで、ゲーム進行には使わない。
- **一致/不一致をボット別に記録する**(§8.4)。`spin_mismatches` と `attack_mismatches_same_spin` を分ける。
- 不一致は**想定内**。レポートに「相手は S2 非対応なので採点が一致しないのは当然」と明記する。
- **相手の攻撃もレフェリーの S2 採点で計算する。** つまり CC2 / clys は「S2 の攻撃値を知らないまま、S2 の攻撃値で戦う」。これは不公平ではなく、**ルールの適用はレフェリーの権限**であり、両者に同じ規則が適用される。
- **相手の攻撃量を相手の申告値で置き換えない**。相手の盤面で起きた消去に対して、レフェリーが S2 の式で攻撃を計算する。
- 相手が S2 を知らないことによる不利は**相手側の制約**であり、我々の勝率の解釈に含める(レポートに明記)。

> attax も同じ扱い(§12.6 の実測: spin 不一致 12/730、同 spin の攻撃不一致 0)。**3 相手すべてについて「レフェリーが S2 で採点し、相手の申告値は監査用に記録するだけ」**という一貫した方針にする。

### 7.3 サードパーティボットへの互換パッチ(開示義務)

CC2 と clys は我々のレフェリーの前提(spawn が row 21、空の hold を表現できる)を満たさないため、**互換パッチを当てないと正常にプレイできない**。パッチは許容するが、**開示と方向性の制約**を課す。

#### 許容されるパッチ

- **プロトコル互換のための修正のみ**。具体的には:
  - spawn 位置の一致(例: CC2 / clys の `y: 19` → `y: 21`)
  - 空の hold の表現(上流が `hold=None` を「queue[0] を hold に移す」と誤解する場合)
  - 盤面・queue・hold の受け渡し形式の一致
- **探索・評価・重み・探索幅・思考時間に触れてはいけない**。

#### 禁止されるパッチ

- 相手を**弱くする**変更(評価項の削除、探索幅の縮小、時間制限の追加など)
- 相手の**判断を変える**変更(合法手の取捨、spin 判定の書き換えなど)
- パッチ内容を記録しない適用

#### 7.3.1 attax の視野パッチ(20 行 → 40 行、2026-11-14 決定)

**attax の upstream `7b38f51` は 20 行視野**。S2 の盤面は 40 行なので、スタックが 20 行に達すると**置ける場所が無いと誤認して 0 候補を返す**。

**確認した事実**(`git show 7b38f51:<path>` で確認。作業ツリーはパッチ適用済みなので使わない):

| 対象 | upstream `7b38f51` | パッチ適用後 |
|---|---|---|
| `movegen.ts` の盤面定数 | **`ROWS = 20`** | `ROWS = 40` |
| TBP アダプタの grid | **20 行**(`length: 20`、`rows[19 - r]`、`board: { rows: 20 }`) | 40 行 |
| 表現できる範囲 | TBP row 19 まで(コメントに明記) | TBP row 39 まで |

**パッチ内容**: 視野を **20 行 → 40 行**に広げる。**それ以外は変更しない**(探索幅・深さ・評価項・重み・思考時間に触れない)。

- **方向**: 相手の可動域が広がる = **相手が強くなる**。§7.3 の許容範囲。
- **記録**: パッチの **SHA-256**、適用方法(`git apply <patch>` など)、適用後のビルドコミットをレポートに記録する。
- **表記**: 「**upstream `7b38f51` + 文書化された視野互換修正(20 → 40 行)**」。
- **理由**: upstream のままでは `forfeit-vision` が勝敗を決めてしまい、**実力の測定にならない**。

**パッチ適用後も attax が forfeit する場合**:

| 条件 | 分類 | 扱い |
|---|---|---|
| 40 行の可視行に完全に収まる合法配置が**無い** | `forfeit-vision` | **本当に詰んでいる**。不戦(勝ちに数えない) |
| 可視行に合法配置が**ある**のに 0 候補 | `forfeit-other` | **アダプタ故障**。ラウンド不成立(§7.4) |

> **`visible_rows` の宣言は、実際に使ったビルドに合わせる**: upstream(20 行)なら 20、パッチ適用(40 行)なら 40。**取り違えると分類が全部狂う**。

#### 開示義務(レポートに必須)

- パッチの**ファイル名・行数・目的**(例: `adapters/cc2-tbp-empty-hold.patch`、116 行、空 hold の表現 + spawn 行)
- **探索・評価に触れていないこと**の明記
- **パッチ適用版のビルドを固定**(upstream のコミット + パッチのハッシュ)
- レポートの表記: 「**upstream `<commit>` + 文書化された互換修正**」
- **パッチは相手を強くする方向にのみ働く**ことの説明(例: spawn を 21 にすると高スタックでの可動域が広がる = 相手の buff)

> **原則**: 互換パッチは「相手のハンディを取り除く」ためにだけ使い、**相手を弱くして勝つ**ためには使わない。パッチの方向性が読めない場合は、パッチなしの結果も参考値として測る。

#### 7.3.2 attax の 180° 回転は**原因ではなかった**(2026-11-16 実測)

**仮説**: attax が 180° 回転に対応していないため、レフェリーが 180° を要求する配置を候補として出し、attax が置けずに forfeit する。

**実測による検証**: レフェリーに `supports_180`(attax = `false`)を実装し、**180° を使わない候補だけを attax に提示**して、既存の forfeit 2 件を再分類した。

**結果: 2 件とも `forfeit-other` のまま。仮説は不支持。**

- attax は **12 候補を返して全滅**していた。レフェリー側には 180° なしでも可視配置がある。
- つまり **180° の欠如は原因ではない**。原因は **board desync(アダプタ側)**。
- **`supports_180` は実装として残すが、attax の forfeit の説明には使わない。**

> **protocol に「attax は 180° 非対応」と書く場合は、この実測結果を併記すること。** 「180° 非対応だから forfeit する」と書くと、**測っていない因果を主張する**ことになる。

### 7.4 アダプタ故障(`forfeit-other`)の定義

**ボットが 0 候補を返したとき、レフェリーの movegen に「そのボットの可視行に完全に収まる合法配置」が存在するなら、アダプタ故障**(`forfeit-other`)。

| 条件 | 分類 | 扱い |
|---|---|---|
| 可視行に収まる合法配置が**無い** | `forfeit-vision` | 相手の視野制限。**不戦**(勝ちに数えない、ラウンドは続行) |
| 可視行に収まる合法配置が**ある**のに 0 候補 | `forfeit-other` | **アダプタ故障**。ゲーム無効、**ラウンド不成立** |

- **`forfeit-other` はラウンド不成立**(§1.4)。相手のアダプタ・我々のアダプタ・レフェリーのいずれかの欠陥なので、原因を特定してから新しい seeds でやり直す。
- **`forfeit-vision` はラウンドを止めない**。不戦として記録し、`TopOut` / `TurnCap` の勝数だけでゲートを判定する。
- **判定に使ってよいのは movegen の結果だけ**(§7.1.2)。`active` の位置やスタック上端で近似してはいけない。
- **attax に 40 行視野パッチを当てた後も同じ規則**(§7.3.1)。40 行で置けないなら本当に詰んでいる(`vision`)、置けるのに 0 候補ならアダプタ故障(`other`)。

## 8. replay と監査

### 8.1 replay の記録項目

1 ゲーム 1 ファイル(JSON Lines)。**verify-replay はこのファイルだけで再実行できる**こと。

```
{"type":"header","schema":"intetrigence/s2-replay/1","seed":12345,"sheet":"A",
 "slots":{"0":"intetrigence","1":"attax"},
 "seats":{"1":0,"2":1},
 "rules":"docs/s2-spec.md@v1.3.4",
 "bots":{"0":{"name":"intetrigence","commit":"...","args":["--ms","100"]},
         "1":{"name":"attax","commit":"...","args":[...]}},
 "started_at":"..."}

{"type":"turn","t":0,
 "placements":[{"slot":0,"piece":"T","rotation":2,"x":3,"y":1,"hold":false,
                "spin":"full","lines":2,"events":[7],"sent":7,"cancelled":0,
                "think_ms":31.2,"candidate_index":0},
               {"slot":1,"piece":"T","rotation":0,"x":4,"y":0,"hold":false,
                "spin":"none","lines":0,"events":[],"sent":0,"cancelled":0,
                "think_ms":28.7,"candidate_index":0}]}

{"type":"garbage","t":0,"from":0,"to":1,"amount":7,"arrival_frame":0}

{"type":"result","winner":0,"reason":"TopOut","turns":87}
```

- **`placements` は seat 順**(解決順)に並べる。verify-replay はこの順で適用する。
- **`placement.piece` を必ず記録する**。袋はプレイヤーごとに独立しているので(§2.2)、hold の後は両者のピースが異なる。verify-replay は**この値**を使う。
- `turn.piece` は**置かない**(v1.1 で削除)。turn 単位の「その turn のピース」は per-player bag では定義できない。参考値が要るなら `placement.piece` を読む。
- `think_ms` と `candidate_index` は監査用。**再実行には使わない**。
- `events` は `compute_attack` の返り値。**再実行時に再計算して一致を検証する**(採点オーディット)。

### 8.2 盤面ハッシュ

各 turn の終わりに盤面のハッシュを記録する(`type:"hash"`)。verify-replay は再実行後のハッシュと比較する。**不一致は即エラー**。

**ハッシュの定義**(実装間で一致させること):

- 対象: **`occupied` 40 行 + `garbage` 40 行の両方**、両プレイヤー分。`garbage` を含めるのは**穴列の差を検出するため**(occupied だけだと穴の位置ずれを見逃す)。
- 関数: **FNV-1a**(64 bit)。暗号強度は不要で、verify の同一性検査には十分。
- タイミング: 各 turn の**両者の設置が終わった後**(§2.3 の解決順序の最後)。

### 8.3 verify-replay

```
verify(replay) -> Result<(), Mismatch>:
    header から seed / sheet / seats / slots を復元
    derive_seeds(seed) で RNG を初期化
    for each turn record in file order:
        for each placement in seat order:
            合法性・到達可能性を再検証
            apply して events / lines / spin を再計算
            記録された値と比較(events, sent, cancelled, spin, lines)
        hash を比較
    result を比較
```

- **探索の再現は不要**(PLAN §3.3)。着手列が記録されているので盤面進行は完全再現できる。
- **ラウンドの全ゲーム**(3 段階 × 50)で verify が通ることを合格条件に含める。

### 8.3.1 測定の完全性(ラウンド成立の条件)

ラウンドが成立するには、**全ゲームについて次が揃っている**こと。

| 成果物 | 内容 | 欠損時 |
|---|---|---|
| replay | 全ゲームの `.jsonl`(着手列・events・盤面ハッシュ) | **ラウンド不成立** |
| verify | 全 replay が `ok=true` | **ラウンド不成立** |
| audit | 全ゲームの `summary.json`(think time・採点オーディット・first-choice) | **ラウンド不成立** |
| 相手の decision log | 相手の `suggestion`(第 1 候補・申告 spin・申告攻撃) | **ラウンド不成立** |

- **1 ゲームでも欠損があれば、そのラウンドは成立しない**。部分的な証拠で勝率を主張してはいけない。
- 欠損は**再開で補える**(§1.4)。同一ビルド・同一 seeds なら、欠損ゲームだけを再実行して揃えられる。
- 相手の decision log は**採点オーディットと first-choice 採用率の根拠**になる。無いと「相手が何を主張したか」を検証できない。
#### 8.3.1.1 相手ごとの decision log の実体

| 相手 | ファイル | 内容 |
|---|---|---|
| **attax** | `logs/<game>-attax.jsonl`(`ATTAX_TBP_LOG`) | `suggestion` の第 1 候補・申告 spin・申告攻撃 |
| **CC2 / clys** | `logs/<game>-opponent.jsonl`(TBP transcript) | `start` / `suggest` / `suggestion` / `play` / `new_piece` の全メッセージ。`suggestion` は**全候補**・申告 spin・申告攻撃 |

- CC2 / clys は**ネイティブの decision log を持たない**。したがって **TBP transcript を decision log とみなす**。
- `arena match --tbp-*` は transcript を**常に書く**。
- **`suggestion` に全候補が含まれること**が必須。第 1 候補だけでは **first-choice 採用率と採点オーディットができない**。
- レポートに**環境変数名とパス**を記録する(`ATTAX_TBP_LOG` など)。パスが再現できないログは証拠にならない。

#### 8.3.1.2 `measurement_complete` は「ファイルの存在」では判定できない(2026-11-16 追加)

**`Path::exists()` は完全性の証明ではない。** 次のどれも `exists() == true` になる:

| 状態 | `exists()` | 実際 |
|---|---|---|
| 0 バイトのファイル(アダプタが起動直後に落ちた) | **true** | **証拠なし** |
| `start` だけ書かれて中断(ゲーム途中で kill) | **true** | **suggestion が無い** |
| 最終行が途中で切れている(バッファ未フラッシュ) | **true** | **JSON として壊れている** |

**したがって `measurement_complete` は内容で判定する**(v1.33 で 3 項目を修正):

| 検査 | 条件 |
|---|---|
| 空でない | サイズ > 0 |
| 完全な行のみ | **全行**が完全な JSON として parse できる |
| **initial `start` がちょうど 1 回** | `reason` の無い `start`。**ゴミ挿入時の再送は `reason: "garbage"` 付きで複数回あってよい** |
| **`suggestion` の件数 == 相手が実際に着手した turn 数** | §8.3.1.3 の注意を参照 |
| 各 `suggestion` に候補が 1 つ以上 | 空の候補列を許さない。**ただし forfeit したゲームの最後の空 `suggestion` は許容**(それが forfeit の記録) |
| `play` の件数 == 相手が着手した turn 数 | forfeit した側は -1 |
| attax の decision log | 行数 == 相手が着手した turn 数 |

> **`suggest` 行は transcript に無い**。TBP transcript が記録するのは `start` / `suggestion` / `play` / `new_piece` で、ホスト側の `suggest` は含まれない。したがって「各 `suggest` に 1 つの `suggestion`」という検査は**できない**(v1.32 の記述は誤り)。`suggestion` は 1 turn に 1 回(リトライは内部)なので、**`suggestion` 件数 == 着手 turn 数**で対応を検査する。

#### 8.3.1.3 「`suggestion` 件数 == replay の turn 数」は**成り立たない**

v1.32 は「`suggestion` の件数 == replay の turn 数」と書いていたが、**これは誤り**。正しい条件は **「相手が実際に着手した turn 数」** で、`turns` との関係は**席順と敗者に依存する**。

**理由**: ゲームは**トップアウトした turn で即終了**し、その turn の残りの設置は行わない(§6.1)。解決順は **seat 1 → seat 2**。したがって:

| 敗者 | その turn に相手が打つか | 相手の `suggestion` 数 |
|---|---|---|
| **seat 1** | **打たない**(seat 1 が先に死んで打ち切り) | `turns - 1` |
| **seat 2** | **打つ**(seat 1 は解決済み、seat 2 が死ぬ) | `turns` |

> **「勝った側は最後の turn を打たない」は誤り**。反例: intetrigence = seat 2、CC2 = seat 1。CC2 が turn N でトップアウトすると、**CC2 は turn N を打って死ぬ**(勝者は intetrigence、CC2 の `suggestion` は `turns` 件)。勝者が最後の turn を打たないのは**敗者が seat 1 のときだけ**。

**実測との一致**(harness-dev、2026-11-16):

| ゲーム | replay turns | CC2 の `suggestion` | 解釈 |
|---|---|---|---|
| CC2 が勝った | 170 | 169 | intetrigence(seat 1)が turn 170 で死んだ → CC2 は打たない → `turns - 1` |
| CC2 が負けた | 209 | 209 | CC2 が turn 209 で死んだ → CC2 は打った → `turns` |

**実装上の要求**: `turns` から件数を決め打ちせず、**replay の各 turn の解決記録から「相手が着手した turn 数」を数える**。席順に依存する条件を `turns` だけから導くと、**席が入れ替わったゲームで誤判定する**(§10.2 の失敗 7 と同じ種類)。

**負のテストが必須**: アダプタを**ゲーム途中で kill** し、`measurement_complete == false` になることを確認する。**正常系だけの確認では、この検査が効いているか分からない**(§10.2 の失敗 7)。

- 代替として、**同じ失敗モード(0 バイト / 途中で切れた最終行 / `start` のみ / forfeit)をユニットテストで再現**する形でもよい。`run_match` に kill フックが無い場合、これが現実的な最小形。

> **「10 ゲームのスモークで `measurement_complete = true` を確認した」は、正常系の確認にすぎない。** 壊れた入力で `false` になることを確かめていない。

### 8.4 監査記録(毎ゲーム)

| 項目 | 用途 |
|---|---|
| 両者の think time(median / p95 / p99 / max) | 計算資源の非対称を公開(PLAN §6) |
| **100 ms を超えた手の件数**(goal の条件) | 「思考 100 ms」を条件にしているため(§2.4) |
| **200 ms を超えた手の件数** | 公称 5 PPS との一致を主張するため(§2.1) |
| **surge 放出回数**(両者) | S2 の勝ち筋(B2B Charging + surge)が機能しているか |
| **最大 B2B streak**(両者) | 溜めがどこまで育ったか |
| **B2B x4 以上だった turn 数**(両者) | 「溜めに到達したか」と「放出したか」を切り分ける |
| 第 1 候補採用率(両者) | attax のフォールバック 0 を確認(PLAN §3.3) |
| 非採用時のインデックス分布 | 同上 |

| 到達可能性検証の拒否件数 | 0 であること |
| attax の `nodes` / `extra.ms` | attax の実仕事量(attax-integration §8-F2) |

| **`max_burst_1`**(1 turn に受けた最大行数、両者) | 単発の最大 |
| **`max_burst_5`**(連続 5 turn で受けた最大行数、両者) | 塊の大きさ |
| **`burst_over_capacity`**(容量超過の窓の数、両者) | **受け止められなかった回数**。崩壊の直接の原因 |

**burst 3 指標の正確な定義**(実装 `crates/arena/src/replay.rs::burst_profile` に一致。2026-11-16 確定):

| 項目 | 定義 |
|---|---|
| **`H`** | **burst 前の高さ**。5 turn 窓の**最初の turn の開始時点**で、**ゴミ挿入の前**に測る |
| **`max_burst_1`** | 1 turn の受信行数の最大。**ゲーム間の最大** |
| **`max_burst_5`** | 5 turn 窓の受信行数の最大。**終盤の 5 turn 未満の窓も含む**(短いゲームでも値が出る)。**ゲーム間の最大** |
| **`burst_over_capacity`** | **オーバーラップあり**の 5 turn 窓のうち `sum > 21 - H` だった**窓の数**。**ゲームごとの値をゲーム間で合計** |

> **`burst_over_capacity` は「burst の回数」ではない。** 窓がオーバーラップするので、**同じ burst が複数回数えられる**。10 ゲームで 53 は「53 回の burst」ではなく「**53 個の窓が容量を超えた**」。レポートで「burst が 53 回あった」と書いてはいけない。
>
> **`H` が「burst 前」である理由**: ゴミが挿入された後の高さを使うと、**挿入そのものが高さを上げる**ので、容量判定が循環する。**「受ける前の余裕」で判定する**のが正しい。

**clys 戦のログ**: `CLYS_TBP_LOG` を**常時有効**にする。実測 **1 ゲーム 174KB(101 turn)**、**50 ゲームで約 8.7MB**。圧縮・間引きは不要。出力先は絶対パスで記録する。

**surge 指標が必要な理由**(2026-11-14): attax 相手の 220 ゲームで **surge 放出が 0 回**だった。評価関数は放出を報酬しているのに実戦で起きていない。原因は 2 つに切り分けられる:

- **B2B x4 に到達していない** → 評価が B2B を維持できていない(溜めの設計の問題)
- **到達したが放出していない** → 放出のタイミングを選べていない(探索・評価の問題)

`max_b2b_streak` と `turns_with_b2b_ge_4` を併記すれば、どちらなのかが分かる。**S2 の勝ち筋を活かせていないことは、勝率と同じくらい重要な診断情報**。

#### 8.4.1 `think_ms` は「探索した」ことを意味しない(2026-11-16 追加)

**`think_ms` は費やした時間の記録であって、探索の記録ではない。** 時間を消費して浅い結果を返す実装は、`think_ms = 100 ms` と記録される。

**実際に起きた事故(2026-11-16)**: `crates/bot` の anytime ループが、期限超過時に**その反復を捨てて `None` を返していた**。呼び出し側は `None` を受けて **1-ply greedy** にフォールバックした。結果:

- すべての設定(depth 8 / 12 / 16、width 2048、1 スレッド)で **1-ply greedy** が選ばれていた
- 毎手 ~105 ms を消費していたので、**`think_ms` は正常に見えた**
- 反復深化が無く、**完了した浅い探索の結果も捨てていた**

**したがって、レポートには次の 3 つを併記する**:

| 項目 | 何を防ぐか |
|---|---|
| `think_ms`(median / p95 / p99 / max) | 時間の非対称の公開 |
| **完了した探索の深さ・幅・ノード数** | **「時間を消費したが探索していない」を検出** |
| **1-ply フォールバックに落ちた手数と割合** | 上記の症状を直接数える |

**「100 ms 思考した」と書くだけでは、探索の有無を主張できない。** 時間は測れるが、探索は測っていなかった。

**`think_ms` の定義**(レポートの数字の意味を固定する):

- **レフェリーが `suggest` を送信してから `suggestion` を受信するまでの実時間**(ホスト側で測定)。
- ボットの自己申告は使わない。attax の `move_info.extra`(自己申告 ms)は **`extra_ms` として別に記録**し、`think_ms` と混ぜない。
- **IPC の往復コストを含む**。attax は subprocess + 行区切り JSON なので、この分だけ `think_ms` が `extra_ms` より大きくなる。レポートでは両方を出し、差を「通信オーバーヘッド」として説明する。

4. 変更後に**同じ grep をもう一度**実行し、古い記述が残っていないことを確認する

> **「実装を直したら文書も直す」は記憶では守れない。grep を手順にする。**

**出典の引用規則(2026-11-15 追加)**:

- **定数の実値を引用する**。`movegen.ts:20` のような**行番号を「値」と読み違えない**。
  - 正しい引用: **`ROWS = 20`(`src/ai/bot/movegen.ts`)** のように、**定数名と値**を書く。
- **作業ツリーと upstream を区別する**。**必ず `git show <commit>:<path>` で確認する**。
- **「既に実装済み」と伝えるときは、どのツリーで確認したかを書く**。**main と相手の worktree は別**(失敗 9)。`git log --oneline -1` で自分の HEAD を確認し、「main の `<sha>` にはある」と伝える。**相手の worktree が古ければ存在しない**。
  - 実際に起きた事故(2026-11-15): 他担当が `adapters/attax-vision-40.patch` を**作業ツリーに適用したまま**にしていたため、作業ツリーを読んで「upstream は `ROWS = 40`」と誤結論し、正しい記述を誤って訂正した。`git show 7b38f51:src/ai/bot/movegen.ts` の 20 行目は **`ROWS = 20`**。
  - **確認手順**: `git status --porcelain` で作業ツリーの変更を確認 → `git show <commit>:<path>` で upstream の実値を読む。
- **相手の仕様は、相手のソースの実値で確認する**。二次資料(自前の分析ノート)だけを根拠にしない。
- **「相手の制約」と「アダプタ故障」を混同しない**。分類ラベルが原因を隠すことがある(`vision` という名前が「相手のせい」に見せていた)。

### 10.3 実装が決めた規則は申告する(運用)

**実装中に「仕様に書かれていない規則」を決める必要が出たら、決めた内容・根拠・影響範囲を spec lead に申告する。** 申告を受けた spec lead は、仕様に追記するか実装を直すかを決め、版を上げる。

この運用が必要な理由は、**仕様の穴は実測でしか見つからない種類がある**から。実際に起きた 8 件のうち **5 件は「実装が正しく、仕様が不十分」**だった:

| 種類 | 実例 | 仕様側の弱点 |
|---|---|---|
| 転記の符号 | §4.3 の front corner 表(y 下向きのまま転記) | 座標表の符号規約を書いていなかった |
| 到達不能の未検証 | §6.1「同時トップアウト → 引き分け」 | 同じ節の別の行と矛盾していた |
| 対象の取り違え | `vision` 判定が「スタック上端」だけだった(実際は active ピースの位置) | どのオブジェクトの位置が問題かを詰めていなかった |
| 規則の空白 | 最大スピン、`start` 再送、`think_ms` の定義、`board_hash` の範囲 | 実装が先に決めていた |
| 実装の暗黙知 | `NoMoves` が到達不能であること | 実装者が気づいて申告するまで不明だった |

**申告の書式**(口頭でよい。記録は spec lead が行う):

1. 何を決めたか(規則の内容)
2. なぜ仕様だけでは決まらなかったか
3. 影響範囲(採点・replay・主張のどれに効くか)
4. 実測があればその数字
