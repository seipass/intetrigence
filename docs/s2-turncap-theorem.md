# TurnCap の定理 — なぜ 1000 turn で決着しないか

**契機**: 9010-B が 1000 turn で未決着(我々 373 送信 / CC2 715 送信、`attack/line` 0.53 対 1.23)。
**目的**: 「未決着になる条件」を式で示し、**回避するための定量条件**を出す。
**日付**: 2026-11-16

---

## 0. 結論

| 問い | 答え |
|---|---|
| `attack/line` 0.53 の構造 | **消去の 53% が single(攻撃 0)**。攻撃の 59% は 44 quad が担っている |
| なぜ 1000 turn も single を撃てるか | **`lines/piece = 0.705 > 0.4`**。**ゴミを来た分だけ消している**ので盤面が上がらない。**「ゴミ処理機」になっている** |
| `defense` が原因か | **違う**。`arrived ≈ 0` なら `defense ≈ 0`。**原因は `height` 項**(single は高さを 1 下げる) |
| 決着の必要条件 | **`S_us > S_them` が持続すること**。そうでなければ**相手にゴミが 1 行も届かない** |
| そのための条件 | **`a_us > 2.5 × S_them / pieces`**。CC2 の `S_them/pieces = 0.715` なので **`a_us > 1.79`** |
| 我々の現状 | `S_us = 373` は **`a_us = 0.53` の理論上限(386)にほぼ到達**。**これ以上は a/line を上げるしかない** |

## 1. `attack/line` 0.53 の構造

9010-B の消去内訳: **single 373 / double 51 / triple 18 / quad 44**(合計 486 回、705 ライン)。

| 消去 | 回数 | 攻撃(combo 0、B2B あり) | 寄与 |
|---|---|---|---|
| **single** | **373(53%)** | **0** | **0** |
| double | 51 | 1 | 51 |
| triple | 18 | 2 | 36 |
| **quad** | **44(9%)** | **5** | **220** |
| combo ln 項・GSB | — | — | 約 66 |
| **合計** | 486 | — | **373** |

**攻撃の 59% は 44 回の quad が担っている。** **single は 53% の消去で 0 行。**

**`attack/line` = 373 / 705 = 0.53。**

### 1.1 なぜ 1000 turn も single を撃ち続けられるか

**`lines/piece = 705 / 1000 = 0.705`。** **ゴミを受けない場合の上限は 0.4**(4 セル/ピース ÷ 10 セル/ライン)。**0.705 は「受けたゴミを消している」ことを意味する。**

**ループ**:

1. 0 ライン設置(**514 回**)→ ゴミが挿入される
2. single(**373 回**)で 1 行消す → 挿入されたゴミを消す
3. 盤面は上がらない
4. 1 に戻る

**つまり我々は「ゴミ処理機」**。**盤面を維持できているのは、攻撃を捨てて処理に徹しているから。** **攻撃を受けていないのではなく、受けたゴミを全部消している。**

## 2. `defense` 項は原因ではない

`defense_value = W × risk(H) × min(arrived, 8)`。

**`arrived`(到着済みのゴミ)が常に 0 に近い状況では `defense ≈ 0`。** **それでも single が選ばれている**なら、**別の項が single を正当化している**。

**原因は `height` / `danger` 項**:

- **single は高さを 1 下げる**
- **quad は高さを 4 下げるが、10 ピースかかる**
- **ピースあたりの高さ削減: single = 1.0 / quad = 0.4**

**ゴミが 0.7 ライン/ピースで来ているとき、`height` 項は single を正しく評価している。** **single は最も高さ効率の良い消し方**。

**したがって「single を減点する」のは誤り**。**減点すると盤面が上がって死ぬ。**

### 2.1 正しい修正: **`height` 項を `risk(H)` でゲートする**

**`height` / `danger` 項が無条件に効いているのが問題。** 盤面が低いときは**高さを下げる価値が小さい**ので、**攻撃に回るべき**。

```rust
// 現状: 高さは常に罰則
value += weights.height * height;

// 修正: 盤面が低いときは高さの罰則を弱める
let risk = ((max_height as f64 - 12.0) / 6.0).clamp(0.0, 1.0);
value += weights.height * height * risk;      // H<=12 で 0、H>=18 で満額
```

**これで「低いときは攻撃、高いときは生存」が自動的に出る。** **`defense` と同じ `risk` を使うのが一貫的。**

**注意**: **`risk = 0` で高さの罰則を完全に切ると、盤面が低いまま積み上がる**。**`clamp(0.2, 1.0)` など下限を設ける**のが安全。

## 3. 定理: 決着には `S_us > S_them` が必要

### 3.1 盤面高さの収支

1 ピースあたりの高さ変化:

```
ΔH = 0.4 − L/P + max(0, S_them − S_us)/P
```

- `0.4` = 1 ピースが 4 セル = 0.4 ライン分
- `L/P` = 1 ピースあたりの消去ライン
- `max(0, S_them − S_us)/P` = **相手の攻撃のうち、我々の相殺を超えた分**

**我々の攻撃 `S_us` は、我々に向かうゴミを相殺する。** **したがって相手に届くゴミは `max(0, S_us − S_them)`。**

### 3.2 相手が死なない条件

**相手に届くゴミが 0**(`S_us <= S_them`)なら:

```
ΔH_them = 0.4 − L_them/P
```

**`L_them/P >= 0.4` なら `ΔH_them <= 0`** → **相手は永久に死なない。**

**CC2 の実測: `L_them/P = 581/1000 = 0.581 > 0.4`。** **CC2 は自己安定。** **我々がゴミを送らない限り、絶対に死なない。**

> **定理**: **`S_us <= S_them` が持続し、かつ `L_them/P >= 0.4` なら、ゲームは TurnCap まで決着しない。**

**9010-B はまさにこれ**(373 <= 715 が 1000 turn 持続)。

### 3.3 決着に必要な `attack/line`

**`S_us > S_them` を達成するには**:

定常状態で `L_us = 0.4P + S_them − S_us`、`S_us = a_us × L_us` を代入:

```
S_us = a_us(0.4P + S_them) / (1 + a_us)
```

**`S_us > S_them` の条件**:

```
a_us(0.4P + S_them) > S_them(1 + a_us)
0.4P × a_us > S_them
```

> **`a_us > S_them / (0.4 × P) = 2.5 × S_them / P`**

**CC2 の `S_them/P = 0.715`** なので:

```
a_us > 2.5 × 0.715 = 1.79
```

> **CC2 を長いゲームで殺すには `attack/line > 1.79` が必要。**

**我々の目標 1.33〜1.40 では足りない。**

### 3.4 我々の送信量は既に上限

`a_us = 0.53`、`P = 1000`、`S_them = 715` で:

```
S_us = 0.53 × (400 + 715) / 1.53 = 0.53 × 728 = 386
```

**実測 373。理論上限 386 の 97%。** **`a_us = 0.53` のままでは、これ以上送れない。**

**したがって唯一のレバーは `a_us`。**

## 4. 「何 turn で決着するか」の式

**`S_us > S_them` のとき**、相手の高さ変化:

```
ΔH_them = 0.4 − L_them/P + (S_us − S_them)/P
```

**決着までの turn 数**(`ΔH_them > 0` のとき):

```
T = (21 − H_them(0)) / ΔH_them
```

**`ΔH_them <= 0` なら `T = ∞`(TurnCap)。**

### 4.1 9010-B に当てはめる

`S_us = 373 < S_them = 715` なので `(S_us − S_them)` は負 → **`max(0, ...)` で 0**。

```
ΔH_them = 0.4 − 0.581 + 0 = −0.181
```

**`T = ∞`。** **1000 turn で決着しないのは必然。**

### 4.2 我々の側

```
ΔH_us = 0.4 − 0.705 + (715 − 373)/1000 = 0.4 − 0.705 + 0.342 = +0.037
```

**1000 turn で +37 行。** **死ななかったのは、ゴミの挿入が 8 行で上限され、余剰が捨てられるから**(`GARBAGE_CAP`)。**モデルより実際は緩い。**

**しかし「じわじわ上がる」状態で、1000 turn を超えれば死んでいた。** **TurnCap は我々を救ったが、勝ちでもない。**

## 5. 実装への要求

| # | 要求 | 根拠 |
|---|---|---|
| **1** | **`height` / `danger` 項を `risk(H)` でゲート**(下限 0.2) | 低い盤面で高さの罰則が効きすぎ、single を選ばせている(§2.1) |
| **2** | **`attack/line` の目標を 1.79 に上げる**(長いゲーム用) | §3.3。1.33〜1.40 では TurnCap を避けられない |
| **3** | **短いゲームでの決着を優先**(burst) | 1.79 は TSD 主体でも難しい。**buffer 21 行を使い切る前に殺す** |
| **4** | **`S_us > S_them` を測定項目に入れる** | 決着の必要条件(§3.2)。**負けゲームの判別にも使える** |

**3 について**: 19 勝は**短いゲームで burst して勝っている**。**TurnCap は 1/20 で、長引いたケース**。**「長引かせない」が現実的な対策**。

---

## 6. 限界

- **モデルは定常状態**(`ΔH` 一定)を仮定。**実際はゴミの挿入が 8 行で上限され、余剰が捨てられる**ので、我々側の上昇はモデルより遅い
- **`L/P` は一定でない**。ゲーム後半で変わる
- **`a_us` を 1.79 に上げられるかは未検証**。**TSD 主体(2.50/line)でも、実際の mix では 1.79 に届くか不明**
- **`S_them/P = 0.715` は CC2 の実測**。**clys / attax では違う値になる**
